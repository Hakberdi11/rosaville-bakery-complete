## Plan items, prioritized

### High impact

1. **Server-authoritative order totals (loyalty + gift-card discount computed server-side)** — Status: Done — `OrderViewSet.perform_create` now re-prices every line from the catalog, derives the loyalty discount from `LoyaltySettings` into the new `Order.loyalty_discount_amount`, clamps gift cards to the order total, and server-derives `amount_paid`/`payment_status` (commit `b7d8ed9`, branch `dashboard-research`).
   - Why: the loyalty research's single most emphatic design rule — "the discount/reward should never be a value a customer or even staff can freely edit at checkout — it should be computed and validated server-side from the accumulated, transaction-backed count, with the redemption itself consuming/resetting that count atomically" (`bakery-ops-research.md:47`). Paper-punch-card forgeability is the named failure mode; a client-supplied total is its digital equivalent.
   - What's wrong/missing today: `OrderSerializer` (`rosaville-backend/operations/serializers.py:115-123`) uses `fields = "__all__"` with `read_only_fields = ["id", "customer", "created_at", "updated_at"]`, so **`total_value`, `gift_card_amount_applied`, `amount_paid` and `payment_status` are all client-writable**. `OrderViewSet` permits unauthenticated create (`CreateOnlyOrIsStaff`, `views.py:168`). `Checkout.tsx:49-55` computes `discount`/`finalTotal` entirely in the browser and POSTs it as `total_value` (`Checkout.tsx:77`). Nothing on the server recomputes the line-item sum from `items[]` against `Dessert.price`, and nothing checks the claimed loyalty discount against `LoyaltySettings.reward_value`. Consequences: (a) anyone can POST `total_value: 0` and get an order; (b) `gift_card_amount_applied` is validated only against the card's balance (`views.py:244`), never against the order total, so a $50 card can be "applied" to a $5 order; (c) loyalty points are then awarded off that same unverified number (`views.py:280`).
   - What it'd take: an `OrderSerializer.validate()` / service function that recomputes the subtotal from `items[]` × current `Dessert.price` (honouring `size_multiplier`), applies the server-loaded `LoyaltySettings` reward when `redeem_loyalty_reward` is validated true, then clamps the gift-card amount to the remaining balance; write `total_value` from that computation and mark it plus `gift_card_amount_applied` read-only on the public create path (staff/dashboard-created orders keep an explicit override path, since walk-in/phone orders legitimately have off-menu totals). Add `Order.loyalty_discount_amount` (new field + migration) to record what was actually granted — this doubles as the redemption record needed by Medium #6.
   - Verification: `curl -X POST /api/orders/` unauthenticated with `total_value: 0` and a real dessert in `items[]`, assert the stored order comes back with the correct computed total, not 0. Then place a real order through `Checkout.tsx` with a reward available and confirm the discount the browser showed matches the persisted `total_value`/`loyalty_discount_amount`, and that `reward_available` flipped to false exactly once.

2. **Waste/spoilage logging — make the existing movement type actually reachable** — Status: Not started
   - Why: the research calls out recording waste itself as independently valuable — "logging what got thrown out (item + quantity + reason) ... because it's the input that lets an owner refine recipes/batch sizes and correct next season's ordering" (`bakery-ops-research.md:17`), and lists "a manual waste log (item, quantity, reason, date)" in the small-bakery-realistic set (`:83`). Cited spoilage range 2–8%.
   - What's wrong/missing today: `StockMovement.MovementType.WASTE = "Waste/Spoilage"` already exists (`operations/models.py:168`) and the Inventory page even colour-codes it (`Inventory.jsx:355`) — but **no UI ever creates one**. The only two write paths are `Inventory.jsx:83` (`adjustInventoryStock(item.id, delta)` with no `reason`/`movementType`, so the API defaults it to `Manual Adjustment`, `views.py:78`) and `Inventory.jsx:282` (stock take → `Stock Take Correction`). So every spoilage event today is silently indistinguishable from a manual correction, and there is no waste report anywhere. The enum is dead code.
   - What it'd take: no migration needed. A "Log Waste" action on the Inventory page opening a small dialog (item, quantity, required reason — a short reason picker like Spoiled/Expired/Damaged/Over-portioned plus free text) posting a negative delta with `movement_type: "Waste/Spoilage"` via the existing `adjustInventoryStock`; plus a waste summary (quantity and dollar value by item and by reason over a date range) reading `GET /api/stock-movements/?ordering=-created_at` filtered to that type — either a panel on Inventory or a section in `Reports.jsx`'s monthly PDF, which already has the COGS plumbing.
   - Verification: log waste against a seeded ingredient; confirm `current_stock` drops, a `StockMovement` row with `movement_type="Waste/Spoilage"` and the reason appears in the item's movement history panel (`Inventory.jsx:360-390`), and the waste summary's dollar figure equals `quantity × cost_per_unit`.

3. **Feedback triage pipeline (owner, urgency, resolution) and a real Feedback page** — Status: Not started
   - Why: `bakery-ops-research.md:63-70` lays out the five-step triage workflow — intake, categorize, **flag urgency**, **assign an owner** ("every item needs a named person responsible for the next action ... no owner, no action"), **close the loop** ("resolution is logged against the original record"). The realistic-scale list (`:88`) asks for "a one-pipeline feedback/review intake with a small set of triage states (new → urgent/routine → assigned → resolved) plus a 'feature this' flag."
   - What's wrong/missing today: `operations.Feedback` (`operations/models.py:279-308`) has only `status` = New/Reviewed/Featured/Archived — **no assignee, no urgency flag, no resolution note, no theme/category tag**. Note "Featured" is modelled as a *status*, which is wrong per the research: featuring is orthogonal to triage state, so a featured review can't also be "resolved," and marking one resolved un-features it from the public testimonials query (`views.py:355`). There is also **no Feedback page at all** — `Layout.jsx:22-77` has no entry for it; the only surface is `components/admin/FeedbackWidget.jsx`, whose sole interaction is toggling Featured (`FeedbackWidget.jsx:20-28`). Staff cannot mark a complaint urgent, assign it, or record what was done about it anywhere. Non-website channels exist as `Feedback.Source` values (Google/Facebook/Instagram/Email) but no staff-facing form can create one, so the "one pipeline" the research asks for has only one working inlet.
   - What it'd take: migration adding `is_urgent` (bool), `assigned_to` (FK to `AUTH_USER_MODEL`, nullable, mirroring `Task.assigned_to`), `resolution_notes` (text), `resolved_at` (nullable datetime), and `is_featured` (bool, backfilled from `status == "Featured"`); repoint `FeedbackViewSet.public` to filter `is_featured=True` and free `status` up for New/In Progress/Resolved/Archived. New `pages/Feedback.jsx` (list + filters for urgent/unassigned/unresolved, detail drawer with assign/urgent/resolve, and a "Log feedback" form for phone/Google/in-person intake) plus a nav entry under Business; keep `FeedbackWidget.jsx` on the dashboard but have it link through, and surface an urgent-feedback event in `Notifications.jsx` (which already aggregates orders/contacts/stock/tasks but treats every review identically, `Notifications.jsx:23`).
   - Verification: submit a review from the public site, mark it urgent + assign it to a staff account, confirm it appears in that user's filtered view and as an urgent entry in Notifications; resolve it with notes and confirm `resolved_at` persists; separately mark a *resolved* review featured and confirm it still appears in `GET /api/feedback/public/` (the bug the `is_featured` split fixes).

### Medium impact

4. **Opening/closing checklists with per-role ownership** — Status: Not started
   - Why: `bakery-ops-research.md:33-41` — the opening/closing checklist is the clearest transferable operational pattern found, and the explicit structural recommendation is to "organize checklist items **by role, not just by department**." The realistic-scale list asks for "role-tagged opening/closing checklists with per-task ownership — a static or lightly configurable checklist feature, not a scheduling engine" (`:85`).
   - What's wrong/missing today: nothing exists — a repo-wide grep for `checklist` across `rosaville-admin-dashboard/src`, `operations/`, and `storefront/` returns zero hits. The nearest neighbour is `operations.Task` (`models.py:311-342`), but it models one-off ad-hoc work: no recurrence, no daily instance, no opening/closing concept, and `module` is a flat label (`General/Production/Inventory/Sales/Marketing/Admin`) with no shift meaning. `Tasks.jsx` is a four-column kanban with no notion of "today's list."
   - What it'd take: two small models — `ChecklistTemplate` (name, shift = Opening/Closing, ordered items each with a `role` and an optional expected duration) and `ChecklistRun` (date, template, per-item completed-by/completed-at) — plus `pages/Checklists.jsx` with a "today's opening/closing" run view (role-filtered for `employee` accounts, same permission shape as `IsAdminOrManagerOrOwner`) and a manager-only template editor. Deliberately no scheduling engine, per `:97`.
   - Verification: define an opening template with items owned by two different roles, start today's run as an employee, confirm only that role's items are actionable, tick them off, and confirm the run shows complete with per-item completed-by attribution and cannot be double-started for the same date.

5. **Stock-take variance tolerance band with required reason codes** — Status: Not started
   - Why: `bakery-ops-research.md:22-25` — "a variance tolerance band is defined per item or per count type ... variances inside the band get adjusted and logged without further action; variances outside the band trigger a recount and a required reason code before the adjustment posts," and the framing that a repeated variance on the same ingredient is a process signal, not a counting mistake.
   - What's wrong/missing today: `Inventory.jsx` has a working Stock Take dialog (`:297-343`) but it posts **every** variance identically — a hardcoded `reason: "Stock take"` with no threshold check and no recount prompt (`Inventory.jsx:282`). There's no tolerance configuration anywhere (`InventoryItem` has `minimum_stock`/`reorder_quantity` but no variance tolerance), and no repeat-variance view: `StockMovementViewSet` supports filtering by item (`views.py:93-98`) but nothing reads it to say "flour has been short three counts running."
   - What it'd take: a `variance_tolerance_percent` field on `InventoryItem` (or a single global default on a settings singleton, which is cheaper and probably sufficient at this scale); in the stock-take dialog, split variances into within-band (post silently, keep the current behaviour) and out-of-band (require a reason selection before the submit button enables, and show a "recount?" confirm); then a small repeat-variance panel that groups `Stock Take Correction` movements by item over the last N counts.
   - Verification: run a stock take with one small and one large variance against a configured tolerance; confirm submit is blocked until the large one has a reason, that both post with distinct reasons visible in the movement history, and that a second oversized variance on the same item surfaces it in the repeat-variance panel.

6. **Loyalty program health metrics on the Loyalty page** — Status: Not started
   - Why: named pitfall in `bakery-ops-research.md:51` — "paper-based programs generate zero usable data — no visibility into participation rate, redemption rate, or program ROI, which matters if the owner wants to actually evaluate whether the program is worth running." Going digital is supposed to buy exactly this.
   - What's wrong/missing today: `pages/Loyalty.jsx` is 87 lines of pure settings form — enable toggle, purchases required, reward type, reward value — and displays **zero data**. Worse, redemption rate isn't currently derivable at all: `OrderViewSet.perform_create` consumes a reward by writing `reward_available: False` in a bulk `.update()` (`views.py:284`) with no record of the redemption, the reward value, or which order consumed it. `Customer.loyalty_points` accumulates but is never spent or reported on beyond a single number in the customer drawer (`Customers.jsx:205`).
   - What it'd take: depends on High #1 landing first (the `Order.loyalty_discount_amount` field it adds *is* the redemption record). Then a stats strip on `Loyalty.jsx`: customers enrolled vs. total, how many currently have `reward_available`, rewards redeemed over the last 30/90 days, total discount value given, and average order value of reward-redeeming vs. non-redeeming orders — all computable client-side from `/api/customers/` + `/api/orders/`, no new endpoint.
   - Verification: place two orders where one redeems a reward; confirm the redemption count, discount total, and the redeeming-vs-not AOV comparison all move by the expected amounts, and that the counts survive a page reload (i.e. they're derived from persisted data, not local state).

7. **FEFO ordering surfaced where stock actually gets picked** — Status: Not started
   - Why: `bakery-ops-research.md:9` — FIFO instead of FEFO reportedly wastes 8–12% more ingredients, and "any 'use this stock first' logic should sort by expiry, not intake date."
   - What's wrong/missing today: partially built. `InventoryItem.expiry_date` exists (`models.py:86`) and `Inventory.jsx` shows an Expiring Soon stat card and per-row Expired/Expires-in-Nd badges (`:73,120,169-182`). What's missing is the *ordering* half: the Inventory table's default sort is `-created_at` (the model's `Meta.ordering`, `models.py:92`) — literally intake order, the FIFO default the research argues against — with no expiry sort option; and `Production.jsx`'s batch/bake-list planner, which is where staff decide what to actually pull, shows ingredient shortfalls with no expiry signal at all.
   - What it'd take: an expiry-ascending sort toggle (nulls last) on the Inventory table, and an "expires within the production window" flag on the batch planner's ingredient rows in `Production.jsx`. Frontend-only, no migration.
   - Verification: seed three lots of the same ingredient category with staggered expiries in a different order from their creation order; confirm the FEFO sort orders them by expiry not creation, and that a bake list for a date within an item's expiry window flags that item.

8. **Customer birthday reward** — Status: Not started
   - Why: `bakery-ops-research.md:53` — a loyalty mechanic that "ends at the point of sale" undercuts retention; "small enhancements like a birthday reward or a slow-day bonus multiplier are cited as producing outsized engagement for very little added complexity."
   - What's wrong/missing today: `operations.Customer` has no birthday/date-of-birth field at all (`models.py:7-47`), and `LoyaltySettings` (`models.py:379-406`) has only the purchase-count rule. There is nothing that gives a customer a reason to think about the bakery between visits.
   - What it'd take: `Customer.birthday` (nullable `DateField`, month/day is what matters) + an optional `birthday_reward_enabled` on `LoyaltySettings`; a birthday input in the `Customers.jsx` detail drawer; a "birthdays this week" list on the dashboard or in `Notifications.jsx`; and either a manual "grant reward" button or a small check that sets `reward_available` on the day. Keep it manual-grant first — automatic granting needs a scheduled job, which this stack doesn't have.
   - Verification: set a customer's birthday to today, confirm they appear in the birthdays list, grant the reward, and confirm the storefront checkout shows the reward as available for that account (`Checkout.tsx:48`).

### Low impact / nice-to-have

9. **Two-shift labelling on tasks/checklists (production vs. retail)** — Status: Not started
   - Why: `bakery-ops-research.md:31` — bakery ops structurally split into an early-morning production shift and a retail/counter shift, "commonly staffed and scheduled as distinct blocks," while explicitly noting this needs "a manual weekly schedule with two shift types ... not an algorithmic scheduling engine" (`:86`). Deliberately low: a full weekly schedule feature is more surface than the finding justifies on its own.
   - What's wrong/missing today: `Task.module` (`models.py:333`) is a flat string defaulting to `"General"` with a UI-side list of `General/Production/Inventory/Sales/Marketing/Admin` (`Tasks.jsx:15`) — no shift concept. Nothing anywhere distinguishes bake-shift work from counter work.
   - What it'd take: cheapest version is to reuse the shift field introduced by Medium #4's `ChecklistTemplate` and add an optional `shift` tag to `Task`, with a shift filter on `Tasks.jsx`. Only worth doing after #4 exists; building a standalone weekly scheduler is not recommended.
   - Verification: tag tasks to each shift, confirm the filter partitions the kanban correctly and that untagged tasks still appear under "All."

10. **End-of-day markdown / donation list** — Status: Not started
    - Why: `bakery-ops-research.md:15-16,84` — day-old markdown and donation programs (the Panera Day-End Dough-Nation pattern, scaled down to "a simple end-of-day list of what's left, and a standing relationship with one or two local charities"), with Good Samaritan Act liability protection cited as the enabler.
    - What's wrong/missing today: nothing exists (no `donation`/`markdown` hits anywhere). The deeper blocker is a data-model gap the research doesn't anticipate: **Rosaville tracks ingredient stock only.** `InventoryItem` is ingredients, and `Dessert` (`catalog/models.py:4-54`) has no on-hand/baked-today count — so there's currently no record of "what's left at close" to build a list from. This is why it's ranked low despite the research rating it realistic: the prerequisite is a finished-goods-on-hand concept, which is a genuinely larger change than the feature itself.
    - What it'd take: either (a) a lightweight `EndOfDayLog` (date, dessert, quantity left, disposition = Sold-down/Marked-down/Donated/Discarded, recipient) that staff fill in manually without any finished-goods inventory behind it — cheap, and still produces the waste-analysis input the research values; or (b) proper finished-goods tracking on `Dessert`, which is a much bigger scope decision and should not be taken as part of this plan without asking first. Recommend (a).
    - Verification: log an end-of-day entry per disposition type, confirm it persists and rolls into a weekly "what we're consistently over-baking" summary alongside the waste log from High #2.

## Explicitly not planned

Per `bakery-ops-research.md:91-97`, and confirmed as absent-and-should-stay-absent in the code: statistical/ML demand forecasting beyond the existing `calculateWasteRisk` usage-rate signal; multi-location inventory transfer or allocation; loyalty tiers/points-to-status ladders (High #1 hardens the existing single punch-card mechanic rather than growing it); ticketing-grade feedback SLAs and auto-escalation (Medium #3 stops at urgent/assigned/resolved); continuous or RFID-backed cycle counting (Medium #5 is a periodic-count tolerance rule, nothing more); and algorithmic staff scheduling optimised against forecast demand.
